# Azure foundation

This folder holds the platform team's foundation: the Azure resources that exist before any developer makes a request. [`main.tf`](main.tf) is the complete bootstrap Terraform root. Supply an existing, dedicated resource group with `resource_group_name`; Terraform does not own or delete that group. Supply exactly one of `learner_object_id` (no directory lookup) or `learner_upn` (Terraform resolves the existing user through Microsoft Graph). An authorized bootstrap identity creates the infrastructure and grants access. The UPN path requires directory-read access as described in the runbook; the object-ID path does not require Entra tenant administration.
Use the [bootstrap runbook](../setup/README.md) for required inputs, provider registration, a fresh working directory, metadata export, and ordered teardown. Do not reuse any other Terraform state from this directory; its resource addresses will not match.

Terraform owns the Crossplane Helm release on the control cluster, pinned to chart `2.4.2`. The Helm provider gets Entra tokens through `kubelogin` using the Azure CLI session; it does not use local cluster certificates or a learner kubeconfig. Run Terraform with Azure CLI signed in as the same bootstrap identity, with access to the control-cluster API. Azure CLI and kubelogin must be installed on the Terraform runner. Cluster role assignments precede the Helm install. The learner's `setup/bootstrap.sh` does not install or configure controllers. If a Crossplane Helm release already exists on the control cluster outside this state, import it into this Terraform state before applying; do not install a second release. No state migration is performed by learner bootstrap.

The controller's separate single-file root is [`src/platform/opentofu/managed-namespace/main.tf`](../src/platform/opentofu/managed-namespace/main.tf). Never apply it locally against controller-owned state. It creates the namespace after the learner submits the environment request, together with a managed identity, federated credential, model-access assignment, and telemetry-publisher assignment per agent, and an OTLP-enabled Application Insights resource. Bootstrap owns the shared model and workspaces, not the `beans` application resources.

The controller package is pinned to provider-opentofu `v1.1.10` in [`packages.yaml`](../src/platform/bootstrap/packages.yaml). Its module pins AzureRM `5.9.0` from `registry.opentofu.org/hashicorp/azurerm` and AzAPI `2.13.0` from `registry.terraform.io/Azure/azapi`, matching the committed `.terraform.lock.hcl`. The OpenTofu registry address avoids the controller runtime's automatic HashiCorp lock-entry migration to an additional, uninstalled provider address. The separate bootstrap Terraform root retains its Terraform registry sources. AzureRM manages the identity, federation, role assignment, and Application Insights; AzAPI manages the ARM namespace. Keep provider constraints, source addresses, and the lock file aligned when publishing a module revision. These pins do not replace a live rehearsal.

The provisioner retains namespace, state-storage, and read access. Bootstrap grants Managed Identity Contributor and Monitoring Contributor on the lab resource group. A conditioned RBAC Administrator grant on the model account permits only `Cognitive Services OpenAI User` assignments to service principals. A separate subscription-scoped delegation permits only `Monitoring Metrics Publisher` assignments to service principals, because Azure creates the application's DCR outside the lab resource group. The trusted module assigns that role only on the vended application's DCR. These are platform-identity permissions, not unrestricted Owner access or developer permissions.

The learner workflow does not require or grant IAM administration.

Terraform permanently purges the Cognitive Services account when destroying that resource, rather than leaving it soft-deleted. The identity running teardown needs `Microsoft.CognitiveServices/locations/resourceGroups/deletedAccounts/delete` at subscription scope; resource-group-only Contributor access is insufficient. See [purge permissions](https://learn.microsoft.com/en-us/azure/ai-services/recover-purge-resources#purge-a-deleted-resource). This setting does not purge accounts deleted outside Terraform.

## Direct application telemetry

Application telemetry does not use AKS `appMonitoring`, an `Instrumentation` CRD, a cluster DCR association, or a collector pod. The module reads the Azure-managed DCR and DCE, discovers the direct metrics stream, constructs the signal-specific cloud URLs, and grants each agent `Monitoring Metrics Publisher` on that DCR. The baseline supplies those URLs, the Application Insights routing attribute, and the required metrics settings through `platform-context`. Local Application Insights authentication is disabled.

The application must authenticate OTLP HTTP requests with its workload identity, request tokens for `https://monitor.azure.com/.default`, and refresh them before expiry. A connection string is not an OTLP bearer credential. Traces and application logs go to the shared Log Analytics workspace; application metrics go to the Azure Monitor workspace. `fourth-coffee-mcp` has no Azure identity, so its SDK telemetry is disabled; its stdout remains available through `kubectl logs`.

The pinned Fourth Coffee release implements authenticated export. The [application artifact prerequisite](../setup/README.md#application-artifact-prerequisite) records the verified image and upstream chart and the live checks still required before delivery. Do not label template checks as a successful native-ingestion rehearsal. To switch an existing lab to Fourth Coffee, follow [the migration steps](../docs/appendix-a-troubleshooting.md#switch-an-existing-lab-to-fourth-coffee).

Cluster infrastructure monitoring is separate: `main.tf` enables omsagent, Container Insights, and managed metrics. Their agents are not required for the application's direct export, and their collection and cost should be reviewed separately. The workshop uses `kubectl logs` for container output.

## Argo CD identity

Argo CD uses workload identity for remote-cluster access, without Entra SSO for the local UI. The extension settings explicitly project a service-account token into the application-controller and server, set the Azure identity environment variables, and annotate their ServiceAccounts with the existing deployment identity's client and tenant IDs. Both ServiceAccounts have federated credentials using the control cluster's OIDC issuer. The extension's built-in workload-identity helper is disabled: the installed chart applies that helper to repo-server access and server SSO, not application-controller deployment access. GitHub repository access remains token-based; repo-server does not need the deployment identity. The projected tokens use audience `api://AzureADTokenExchange`, expire after one hour, and are rotated by Kubernetes. This avoids the extension's Helm settings interface coercing the webhook's `"true"` pod label into a boolean.

After an extension configuration update, check the newly created controller and server pods for `AZURE_FEDERATED_TOKEN_FILE` and a readable projected token volume. This explicit projection does not require the workload-identity webhook label. Do not print the token. `federated token file cannot be empty` means this pod wiring is missing, not that the identity needs broader Azure permissions. Keep checks bounded to two minutes and inspect the current error instead of waiting repeatedly.
